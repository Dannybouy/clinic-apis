## 1. PR 1, backend: level 5 rate limiting

**Rule:** at most 5 `POST /bookings` attempts per email per minute, failed attempts included. The 6th attempt gets 429 with a `Retry-After` header in whole seconds. Other emails are unaffected.

**Design (decided)**

- **Storage:** in memory, in a new file `backend/rate_limit.go`.
  - `type rateLimiter struct { mu sync.Mutex; attempts map[string][]time.Time }`. This is a sliding window: each email keeps the timestamps of its attempts in the last 60 seconds.
  - `allow(email string, now time.Time) (retryAfter int)` returns 0 when the attempt is allowed and records it. Otherwise it returns `ceil(oldest + 60s − now)` seconds.
  - `reset()` empties the map.
- **Wiring:** add `limiter *rateLimiter` to `apiConfig` and create it in `main.go`.
- **Placement in `handlerCreateBooking`:** decode the body, then trim and lowercase the email, then do the rate-limit check, then the idempotency logic, then validation and the booking.
  - The check runs before validation, so failed attempts count.
  - Idempotent replays count too.
  - If the email is empty after trimming, return 400 without counting the attempt.
- **429 response:** call `w.Header().Set("Retry-After", strconv.Itoa(n))` before `respondWithError(w, 429, "too many attempts for this email", nil)`. Headers can't be added after the status is written.
- **`/reset`:** call `cfg.limiter.reset()` after the commit succeeds.
- **Scope:** `GET` endpoints and `DELETE` are not rate-limited.

**Check it by hand:** 6 quick POSTs with the same email give five non-429 responses, then a 429 with `Retry-After` between 1 and 60. A different email still works. After `/reset`, the same email works again.

**Release:** this needs no migration. Run `gofmt -w backend`, open a PR, wait for the checks, merge, and confirm the live site returns a 429 on the 6th attempt.

### 2.3 Layout

- **Header:** brand, a health dot, an email chip, a **Demo controls** button and an **Inspector** toggle.
- **Tabs:** **Find a slot** and **My bookings**. The active tab is kept in the URL hash (`#book` or `#bookings`) so a refresh keeps your place.
- **API inspector:** a panel on the right on desktop, open by default. On mobile it's a bottom sheet, closed by default.

### 2.4 Email

- `useRememberedEmail` stores the email in `localStorage` (key `koya.email`).
- The email chip shows the current email and has a **Switch** option.
- The booking dialog's email field and My bookings both use it.
- Once a booking succeeds, its email becomes the remembered one.

### 2.5 Find a slot

- **Provider chips:** "All doctors" plus one chip per provider, built from the list of slots. Picking one calls `GET /slots?provider=…`, so the request appears in the inspector.
- **Slot list:** slots are grouped by local day. Each slot is a time button:
  - free: clickable
  - `available:false`: greyed out with a **Booked** badge
  - start time in the past: a **Started** badge, not clickable
- **Empty list:** "No appointments yet" with a **Load sample schedule** button.
- **Network error:** an inline message with **Try again**.
- **Times:** shown in the visitor's local timezone with a label such as "Thu 10 Dec, 10:00 (GMT+1)". The inspector shows the raw UTC values.

### 2.6 Booking dialog

- **Contents:** the doctor and time, a name field, and the email field (prefilled). The form checks that both are filled and that the email looks valid.
- **Idempotency key:** one `crypto.randomUUID()` is created when the dialog opens, and every submit from that dialog sends it as `Idempotency-Key`. **Try again** after a network failure reuses the same key.
- **Responses:**

| Response | What the dialog does |
| --- | --- |
| 201 | Shows a confirmation with the booking ID, a **Copy** button and **View my bookings**. The slot list refreshes. |
| 400, 404, 409, 422 | Shows the `error` text from the API inline. |
| 429 | Shows exactly: *"Too many attempts for this email. Try again in N seconds."* N comes from `Retry-After`. No countdown. |
| Network failure | Shows a message with **Try again**, using the same key. |

### 2.7 My bookings

- **List:** `GET /bookings?email=…&limit=10`, oldest first.
- **Page size:** a selector offering 5, 10 and 50. Changing it reloads from the first page.
- **Load more:** appends the next page using `next_cursor`. It's hidden when `next_cursor` is `null`.
- **Booking card:** status badge (confirmed or cancelled), doctor and time, booking ID with **Copy**, and created time.
  - The doctor and time come from looking up `slot_id` in the slots already loaded by `GET /slots`. If the slot can't be found, the card shows "Slot {id}".
- **Cancel:** confirmation dialog, then `DELETE /bookings/{id}`. The card switches to **Cancelled** and the slot list refreshes, so the slot shows as free again.
- **Find a booking by ID:** an input that calls `GET /bookings/{id}` and shows the booking card, or "No booking with that ID" on a 404.
- **No email set:** prompt the visitor to enter one.

### 2.8 API inspector

- **Each entry:** method, URL, a status badge coloured by range (2xx green, 4xx amber, 5xx red) and the duration in milliseconds.
- **Expanded entry:** request headers (including `Idempotency-Key`), request body, response headers (including `Retry-After`), and the response body pretty-printed.
- **Actions:** **Copy as curl** on each entry, and **Clear** for the whole list.
- **Behaviour:** keeps the last 100 entries in memory only, and briefly highlights each new entry.
- **What it logs:** every call made through `api/client.ts`, including the scenario requests and the health checks.

- **Shared data:** Load sample schedule and the scenarios write to the same live database every reviewer uses.
- **Neon password:** it was typed into a terminal, so it's in shell history. Reset it in Neon, then update Render and `.env.neon.local`.
